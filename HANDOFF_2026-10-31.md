## 5. New implementation in the 31 October session: retry local output in Wails

### User-visible behavior

When a session has captured every configured photo and produced `rendered.jpg`, but no final local `photo.jpg` was published, the Wails result screen now shows **Retry local save**.

The action:
- Reuses the same session ID and preserved rendered image.
- Does not reopen the camera, recapture or rerender.
- Shows a saving state and disables starting another session during the retry.
- On success, changes the session to completed, sets the output path and enables Show saved photo.
- On failure, keeps the rendered session and diagnostic so the operator can resolve the issue and retry again.

### Shared implementation

- `internal/booth/output/retry.go`: shared `output.RetryLocalFromSession` validation and orchestration used by the CLI and Wails.
- `internal/booth/output/local.go`: adds `SaveExclusive`. It copies to a same-directory temp file, syncs/closes it, then uses a hard link to publish the final path without replacing an existing photo. This makes concurrent retries safe against overwriting the destination on filesystems supporting hard links. On unsupported filesystems it fails rather than overwriting.
- `internal/booth/output/retry_test.go`: success, capture/render preservation, invalid/missing input, overlapping roots, symlinked session, cancellation, existing-output refusal and concurrent retry tests.
- `apps/output-retry/main.go`: now calls the shared core API instead of maintaining a separate validation implementation.
- `tools/ui-spike/wails-v2/player.go`: adds `RetryPhotoOutput`, `OutputRetrying` state and session guards.
- `app.go`, `settings.go`, `packages.go`: guard conflicting session/settings/package changes while output retry is active.
- `app_test.go`: tests save-only retry to completed, same ID/capture preservation, wrong/already-completed session, incomplete captures and mutation/concurrent retry guards.
- `frontend/src/main.js`: result-screen state, retry button, saving state, output diagnostics and event handler.
- Wails binding generation added `RetryPhotoOutput` and `PlayerSession.output_retrying` to `frontend/wailsjs`.

### Safety properties

The shared API validates:
- A 32-character lowercase hexadecimal session ID and configured capture count.
- Separate/non-overlapping session and output roots.
- Real non-symlink session/capture directories.
- Every expected capture and the preserved rendered JPEG as non-empty regular files.
- No existing `photo.jpg` at the destination.

The final no-overwrite check is enforced again atomically during publication. The old session captures and rendered image remain intact.

## 11. Addendum — Live Camera Preview implementation (2026-10-31)

### Architecture and code changes

- Added optional `camera.PreviewProvider`; the core `camera.Provider` contract remains unchanged.
- Windows Media Foundation `Preview` reads from the same `captureWorker` and same validated/normalized MJPEG frame path as `Capture`. `Preview`, `Capture`, and `Close` serialize through the provider operation mutex; no second native reader/stream is opened.
- Recovery decorator gained `Preview(ctx)` and uses the existing bounded close/reopen recovery policy only for stream-invalidated preview reads. Cancellation and non-stream errors are not retried.
- Wails preview runs only on the idle/home screen. It stops/closes before real or demo capture, operator Settings, and shutdown. The stop barrier waits for worker cleanup; on Close/read timeout or error it fails closed and will not create a second camera provider. Native Close failure remains latched.
- Important startup cancellation fix: `windowsBackend.Open(ctx)` previously returned immediately on cancellation and left a background cleanup goroutine to close the native worker. It now waits for the worker's startup result and closes it synchronously before returning; if cleanup fails, the worker reference is retained so Close can retry. If native startup never returns, the Wails 7-second barrier times out and refuses capture. Unit tests cover both successful and failed startup cleanup paths.
- Preview frames are JPEG data URLs carried through Wails events only; they are not persisted in the session/output folders or uploaded. At most one frame is in flight, max rate 5 FPS, exact-sequence ACK after successful image load/decode, duplicate/stale ACKs rejected. WebView decode errors are not ACKed. 2-second ACK timeout stops a stalled preview.
- Frontend has idle preview stage, local-only label, reconnect/unavailable state, explicit Retry button and cleanup behavior when image decode fails. If Start or Settings loading fails before switching away from idle, the UI attempts to resume preview.
