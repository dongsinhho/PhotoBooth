## Implemented in the current working tree: crash/restart recovery

### Domain and persistence

- Added `internal/booth/session/manifest.go` with strict, bounded schema-v2 session manifest for new sessions (schema-v1 remains backward-readable) and four phases: `preflight`, `capturing`, `rendered`, `output_finalized`.
- Manifest records session ID, expected/completed shots, frame path + SHA-256, run-config fingerprint, config schema version, camera/capture metadata, demo flag and phase timestamps.
- Manifest JSON rejects unknown fields, multiple JSON documents, invalid versions/phases, inconsistent shot counts/timestamps and incorrect session-directory identity.
- `WriteManifest` writes/syncs/closes a same-directory temporary file before atomic replacement:
  - Windows: `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`.
  - Non-Windows: rename followed by parent-directory sync.
- Added `workflow.NewSessionManifest` to fingerprint the original configured frame bytes and capture-affecting configuration. The follow-up snapshot step is recorded below.
- Workflow persists state after initial preflight, after camera-open/capturing transition, after each successfully validated JPEG, after render validation and after successful local output publication.
- Existing captures are now decoded as JPEGs before a resume can proceed. A failed capturing-phase manifest write after camera open is covered by a regression test and closes the camera.
- A full-capture resume can proceed directly from Preflight to Rendering without opening a camera. Partial resume captures only missing shots.
- New workflow sessions still claim a never-used session directory atomically. Explicit resume remains separate and requires the expected durable manifest and exact known workspace contents.

### Atomic capture-file staging (implemented in this continuation)

- `camera.CaptureRequest.OutputPath` is now explicitly a caller-owned staging path. Each attempt writes to `captures/.staging/shot-NN-<random>/capture.jpg`; provider-internal temporary files remain inside that attempt directory.
- After capture returns, the workflow checks the exact returned path, rejects symlinks/non-regular files, fully decodes the JPEG, syncs the staged file, then publishes to `captures/capture-NN.jpg` with a no-replace atomic operation.
  - Unix: `os.Link` atomically creates the final name without replacement, syncs the captures directory, removes the staged name, then syncs the attempt directory and its staging parent after cleanup.
  - Windows: `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` and deliberately without `MOVEFILE_REPLACE_EXISTING`.
- If publication reports a destination collision, the existing final artifact is preserved. Unsupported hard-link filesystems fail safely; there is no fallback to an overwrite-capable rename.
- Read-only recovery discovery recognizes only the bounded `.staging/shot-NN-<32-hex>/` layout and known camera temp artifact names. It never deletes staged files. Unknown names, symlinks, oversized staging trees or other entries remain inspect-only.
- When the operator explicitly chooses Continue, the workflow fully validates committed captures, reconciles exactly one `capture-NN.jpg` published just before a crash interrupted the manifest update, then removes the validated stale staging tree and captures remaining shots. A gap larger than one or any invalid committed JPEG is still inspect-only.
- Added regression coverage for partial-write isolation, read-only staging discovery, unknown staging artifact rejection, explicit Continue cleanup/retake, post-publication manifest reconciliation and no-overwrite collision behavior.

### Read-only discovery and operator UI

- `session.InspectRecoveryRoot` inspects only the configured sessions root. It never creates, renames, repairs, resumes or deletes data.
- Rejects root/session/captures/staging symlink or junction redirection, unexpected layouts, invalid committed JPEGs, missing/corrupt/unsupported manifests and manifest/file mismatches other than the single documented post-publication capture lag.
- Discovery is bounded: at most 4,096 root entries; three entries per session folder; up to twelve sequential committed captures plus an optional staging directory containing at most twelve bounded attempt directories.
- Wails startup calls recovery discovery before idle camera preview begins.
- Home screen now shows an **Interrupted sessions** panel with:
  - **Continue session** for a manifest/file/config-matched preflight/capturing session.
  - **Retry local save** for a fully rendered session with no ambiguous existing output.
  - **Start a new session** (confirmed) with a new ID while preserving the old folder.
  - **Inspect / export files** and **Hide for now**.
- Continue re-scans and the workflow re-reads/revalidates the manifest and fully decodes each committed JPEG before camera use. It reconciles only one published-but-unrecorded capture, then cleans only validated staging artifacts and captures missing shots.
- Output-only recovery reuses `rendered.jpg`; it does not open the camera or renderer. It refuses ambiguous/temp/existing output and never overwrites `photo.jpg`.
- Recovered output retry now claims `outputRetrying` and sets the UI session under one app mutex critical section, closing the race where a new session could replace `a.player` between state setup and retry.
- Review hardening: startup discovery uses bounded, header-only JPEG checks (40 MiB file cap, 8,000-pixel side cap, 40M-pixel cap) so startup does not full-decode every guest photo. The workflow fully decodes every preserved capture before a resumed camera session opens; output-only recovery fully decodes `rendered.jpg` before publication.

Uncertain preview cleanup or invalid/truncated rendered JPEG fails closed without publishing output. If retry is refused, the frontend re-attempts idle preview; the synthetic-only guard keeps preview disabled.
- Recovery discovery treats non-`NotExist` `Lstat(rendered.jpg)` errors as inspect-only instead of treating permission/I/O errors as a missing render. Inspect/export is blocked while output retry is active.
- Added regression coverage for JPEG header-vs-full-payload validation, truncated resumed capture rejection before `Camera.Open`/next capture, truncated rendered-output retry rejection, preview-cleanup failure, and synthetic-only idle-preview/Restart guards.

### Conservative failure boundaries

- Missing/corrupt/legacy manifest or unknown entries => inspect-only.
- Partial camera writes remain under `.staging`; discovery is read-only and explicit Continue cleans the validated attempt before retaking the missing shot. One committed capture ahead of a capturing manifest can be reconciled only after full decode on Continue; larger count gaps, invalid committed JPEGs or unknown staging layouts remain inspect-only.
- Crash after render but before output publication => output-pending and explicit save-only retry.
- Crash after local publication but before output-finalized manifest update => inspect-only to avoid duplicate/overwriting output.
- Capture-file staging is now implemented. A provider never receives a committed `capture-NN.jpg` path; only a fully decoded and synced staged file is atomically published without replacement.
- Recovery never deletes committed captures, rendered photos, final outputs or whole session folders. Only validated uncommitted `.staging` artifacts are cleaned after explicit Continue; retention remains a separate opt-in reviewed-plan operation.
