## Why the adapter is not wired into Wails yet

A Windows spooler job ID is not a durable physical-print completion record. There is an ambiguity window if the app crashes after the OS accepts a job but before PhotoBooth persists the returned job ID/status. Blind retry could produce duplicate paper output.

Before enabling printing in Wails guest sessions, design and implement:
1. Explicit printer-enabled/queue/form/orientation settings (safe default disabled) and schema migration.
2. Durable print intent before spool submission.
3. Persistence of the returned Windows spooler job ID and output-target status.
4. Conservative crash recovery/reconciliation for ambiguous jobs; never blindly re-submit.
5. Operator-visible queued/failed/uncertain states and a provider-specific reconciliation action.
6. A bounded strategy for synchronous driver calls; context cancellation cannot forcibly interrupt a blocked StartDocW/EndDoc call.
7. Physical acceptance on the selected real printer/media before claiming printer support.

The adapter currently inherits the queue's default form; named media/form selection is not exposed yet. Do not apply the virtual queue's FlipVertical transform to physical hardware without a separate orientation test.

## Continuation update - kernel-verified printer lock ownership (2026-11-19)

Implemented Windows kernel-held printer lock leases and safe reconciliation for versioned locks.

### Lock lease

- Added PrintLockLease platform abstraction. On Windows, CreateFileW creates .print.lock exclusively with write/delete access and sharing restricted to read-only observers. The DurablePrinter process holds this handle from before manifest intent publication until after spooler result persistence.
- The marker now carries lease_version=1, owner_pid (diagnostic only), attempt ID, queue, deterministic document name, rendered-source SHA-256 and creation timestamp.
- Windows releases the handle when the owning process exits, including abrupt termination. Liveness is established by an exclusive file-handle claim, never by PID. This avoids PID reuse errors.
- Read-only scanner uses a dedicated Win32 read handle with compatible sharing, then probes ownership. UI DTO exposes active, orphaned or unverifiable.
- Legacy lease-version 0/omitted locks, corrupt/partial lock files and unsupported non-Windows implementations remain inspect-only. They are not deleted or upgraded based on PID or queue absence.

### Reconciliation workflow

- Recovery exposes Reconcile released printer lock only for version-1 locks classified orphaned.
- The API claims the kernel lease again and retains it through all checks and updates.
- It validates the exact session, lock metadata and full rendered JPEG SHA-256 against the lock.
- If a matching manifest attempt is submitting, it is changed to uncertain. If its queued/uncertain/failed result is already durable, that result is preserved. If the crash happened after lock creation but before PrintAttempt intent publication, one matching attempt is created and persisted as uncertain. A snapshot-backed v2 manifest is reverified before any v3 upgrade.
- The manifest is persisted before the lock is marked for deletion through the held Windows handle. A crash between those two steps can be reconciled idempotently.
- Reconciliation does not query, cancel or submit a spooler job. Afterward, the UI still requires queue inspection followed by the separate operator printed/not_printed/unknown decision.

## Continuation update - Windows release authenticity hardening (2026-11-20)

### Implemented

- Unsigned Preview packages require explicit `-AllowUnsignedPreview` at build/install/start/rollback. The installer denies unsigned packages before activation if the switch is absent. Unsigned manifests remain `release-manifest.json` on the `internal-alpha` channel.
- Signed release candidates use `release-manifest.ps1`, an Authenticode-signed one-line envelope containing a base64 UTF-8 JSON manifest. The installer validates Authenticode status and pinned signer thumbprint **before parsing the manifest payload**.
- The builder can take `-SigningCertificateThumbprint` and `-TimestampServer`. It checks the certificate exists in CurrentUser/My or LocalMachine/My, has a private key, is currently valid and has the Code Signing EKU. It signs staged copies of PhotoBooth.exe and manage-smb-remote-admin.ps1 with SHA-256 plus timestamp, creates/signs the manifest envelope, and packages the signed copies. The original build-tree files are not modified.
- Installer validates envelope publisher, EXE/helper Authenticode signer, file size and SHA-256. It refuses mixed manifest types, untrusted/empty publisher pins, same-version signature-policy/publisher/helper-hash collisions, unexpected archive entries and unsigned packages without explicit Preview opt-in.
