# ADR 0028: Conservative local session crash/restart recovery

- **Status:** Accepted; implemented in the Go workflow/session packages and Windows Preview Wails prototype. Automated synthetic tests and a dedicated synthetic-only Windows Wails UI Automation smoke pass; physical-device validation remains pending.
- **Date:** 2026-11-07

## Context

The current player stores captures, a rendered image and the final local output in session-scoped folders. A process or machine interruption can leave a partially completed session. A directory name or a non-empty captures folder is not enough to prove that its contents are safe to resume: the frame, shot count, camera settings, individual JPEGs and output publication state may not agree.

Recovery discovery must preserve guest photos, avoid duplicate output publication and never open a camera or mutate session data as part of the discovery operation. The existing idle-preview lifecycle may start separately after discovery completes.

## Decision

1. **Persist a versioned session manifest.** Each new session writes a strict, bounded schema-v2 `manifest.json` with identity, phase, expected/completed shot counts, original frame path/digest, immutable frame-snapshot declaration, run-config fingerprint and phase timestamps. The reader remains backward-compatible with schema-v1 manifests, which do not contain a frame snapshot. Unknown fields and unsupported versions fail closed.
2. **Publish manifest updates atomically.** Write to a same-directory temporary file, sync and close it, then replace the manifest atomically. Use the platform-specific atomic replacement implementation.
3. **Make discovery read-only.** Scan only the configured sessions root before the separate idle-preview lifecycle proceeds. Reject symlink/junction redirects, non-child session paths, unknown layouts and oversized directories. Do not resume, repair, delete, open a camera or rewrite data during discovery.
4. **Require manifest/file agreement.** Discovery validates sequential names, bounded regular JPEG files and readable JPEG headers; it matches actual capture count to the manifest and verifies the declared frame snapshot SHA-256 before offering Continue. For schema-v2 sessions, it recomputes the capture/run-config fingerprint using the immutable snapshot and original configured frame path, so later edits/removal of the operator-selected frame do not alter the interrupted session. The schema-v1 fallback still requires the original frame file and matching digest. Exactly one committed capture may be ahead of a `capturing` manifest when a crash interrupts the post-publication progress update; all other count gaps remain inspect-only. Continue fully decodes every preserved JPEG before opening the camera; output-only retry fully decodes its preserved rendered JPEG before publication. Missing, corrupt, unsupported or inconsistent records fail closed.
5. **Stage and atomically publish every capture.** Camera providers write only to a unique `captures/.staging/shot-NN-<random>/capture.jpg` path. After a full JPEG decode and file sync, the workflow publishes to `capture-NN.jpg` with a no-replace atomic operation (Unix hard link + staged-name removal; Windows `MoveFileExW` without `REPLACE_EXISTING` and with `WRITE_THROUGH`). Discovery validates known staging layouts but never removes them. Only an explicit Continue may clean validated interrupted staging attempts and retake missing shots.
6. **Require an explicit operator choice.** Offer Continue, Retry local save, Start a new session, Inspect/export and Hide for now as applicable. Continue captures only missing shots; a full set can proceed directly to rendering. Restart allocates a new session ID and leaves the previous workspace untouched.
7. **Keep output publication exclusive.** An output-pending recovery stops and joins idle preview, fully decodes and reuses only the preserved rendered JPEG. It must not open a capture camera or render again, and it must not overwrite an existing final output. Uncertain preview cleanup or failed JPEG decoding blocks publication.
8. **Do not couple recovery to retention.** Recovery never deletes committed captures, rendered photos, finalized output or whole session folders. The only recovery cleanup is removal of the narrowly validated uncommitted `.staging` tree after explicit Continue. The separate opt-in retention workflow and its reviewed-plan confirmation remain the only supported cleanup mechanism for committed session/output data.

## Consequences

- A process interruption before a valid manifest exists is inspect-only, not automatically resumable.
- A partial camera write is isolated under `.staging` and may be cleaned/retaken only after explicit Continue. A complete published JPEG that is one shot ahead of the capturing manifest can be reconciled on Continue after full decode. Unknown staging layouts, invalid committed JPEGs, unexpected files and larger manifest/count gaps remain inspect-only.
- A rendered session without an ambiguous final output can retry local save without recapturing.
- A crash after final output publication but before manifest finalization is intentionally inspect-only to avoid duplicate or overwriting publication.
- Recovery discovery performs local metadata/JPEG-header inspection only and does not open a camera. After discovery completes, the separate Windows Preview idle-preview lifecycle may open the configured camera while the player remains idle; capture/Continue stops that preview behind the camera lifecycle barrier before the workflow opens a capture provider.
- The feature is currently part of the Windows Preview prototype. It does not certify production UI, Linux behavior or physical camera recovery.
- Schema-v2 sessions atomically preserve the exact declarative frame JSON as `frame.json` in the session workspace and verify it against both snapshot and frame digests. Frame schema v1 contains only geometry, colors, slots and text; it has no external image/font/asset references. Recovery can therefore render from the snapshot even if the current Settings frame is edited, replaced or missing. Schema-v1 legacy sessions remain readable but still depend on the original frame file and matching digest.
- The rest of the station configuration is fingerprinted, not fully archived. Recovery still requires the capture-affecting settings to match; a frame snapshot does not make all historical settings immutable.
- Capture staging is implemented inside the session captures directory and bounded/recognized by discovery. It relies on local-filesystem no-replace publication semantics; unsupported hard-link filesystems fail the capture safely rather than falling back to a potentially overwriting rename.

## Validation

Synthetic tests use temporary directories and generated JPEGs; no real guest photo/session directory is modified. Tests verify manifest strictness/atomic replacement, read-only scan behavior, phase and timestamp invariants, bounds, unknown/legacy layouts, bounded header checks, partial camera output isolation under `.staging`, explicit Continue cleanup/retake, no-replace capture publication collisions, one-published-capture-ahead manifest reconciliation, truncated-payload rejection before camera open or output publication, current-config mismatch, camera cleanup after manifest persistence failure, partial/full capture resume, output-only retry and fail-closed preview cleanup, output no-overwrite, ambiguous output handling and fresh-session restart preserving original manifest/capture bytes.

On 2026-11-07, the original crash-recovery implementation passed root and Wails Go test suites, root and Wails vet, root Windows build, Wails frontend/Windows Preview production build and `git diff --check` on ShinPc. A later snapshot follow-up adds the separate validations below. A dedicated Wails UI Automation smoke passed using an isolated TEMP profile, generated JPEG fixtures, demo/fake-camera recovery, `PHOTOBOOTH_DISABLE_CAMERA_PREVIEW=1` and `PHOTOBOOTH_SYNTHETIC_ONLY=1`. It verified all recovery actions plus backend rejection of the Start with webcam button; diagnostics recorded only `preview_status:disabled`. The physical camera was not opened and all generated test data was removed. Linux runtime validation remains pending.

### Immutable frame snapshot follow-up (2026-11-07)

- New sessions now write a schema-v2 manifest and a session-local frame.json containing the exact frame definition bytes. The snapshot is bounded to 1 MiB, written through a same-directory temp file and synced, then published without replacement (Unix: hard link, temp unlink and directory sync; Windows: MoveFileExW without REPLACE_EXISTING and with WRITE_THROUGH). The manifest records frame_snapshot_file and frame_snapshot_sha256; its value must match the frame-config digest.
- The reader accepts schema-v1 manifests unchanged for legacy recovery, but schema-v1 cannot declare snapshots. Schema-v2 requires a valid declared snapshot. Discovery accepts at most four top-level session entries and treats undeclared, missing, redirected, oversized or digest-mismatched snapshots as inspect-only.
- The Wails recovery fingerprint is recomputed from the preserved snapshot while retaining the original frame path as the fingerprint identity. A changed or missing active Settings frame therefore does not block Continue when the snapshot is valid. Only frame-specific Settings warnings may be bypassed; invalid station profile, camera/provider and other settings errors remain blocking. Legacy v1 recovery still requires the referenced original frame to exist and match.
- Local retention recognizes manifest.json / frame.json and only considers manifested sessions in output_finalized phase with a verified snapshot. Sessions that still have a recovery action available are not eligible for session retention.
- Frame schema v1 contains only local declarative geometry/colors/slots/text; it has no external image/font/asset references. The station config itself is still fingerprinted, not archived.
- Regression tests cover no-replace snapshot creation, hash tampering, recovery discovery, resume after deleting the original frame, legacy v1 compatibility and retention exclusion for corrupt snapshots.
- Root and Wails Go tests/vet passed after the implementation. No physical camera, USB or photo-quality test was needed or run for this filesystem/workflow change. Linux behavior is compile-tested only until a Linux runtime is available.
