# Roadmap and Validation Gates

**Status:** Proposed sequence; dates intentionally unset

## Stage 0 - Self-service readiness and hardware selection
- Select a reference camera/PC/output configuration likely to be available to new booth builders.
- Prepare quickstart, troubleshooting, sample configuration, and voluntary issue/compatibility-report templates.
- Use optional user feedback when it arises; do not require formal interviews or incumbent-store migration.
- Select one camera model, one output path, a Windows baseline, and a specific Linux distribution for the technical spike.
- Verify SDK operations, supported model/OS combinations, license terms, and redistribution rules.
- Validate kiosk behavior, camera trigger/transfer, printing, auto-start, and updates.
- Decide how the pilot will configure local/LAN/cloud delivery and free/paid sessions.
- Choose a verifiable payment-confirmation method before accepting money.

**Exit gate:** self-service setup path is documented, reference hardware/OS test matrix is selected, and a measurable capture-to-output acceptance test is defined. Formal interviews are not required.

**Implementation note (2026-11-07, crash/restart recovery and atomic capture staging):** the root Go workflow/session packages persist a strict schema-v2 session manifest for new sessions (schema-v1 remains readable) with phase, expected/completed shots, frame digest, immutable `frame.json` snapshot declaration, run-config fingerprint and timestamps. Windows Preview startup performs bounded read-only discovery before idle camera preview and surfaces only verified Continue/output-retry states; legacy, corrupt, redirected, unknown or mismatched workspaces remain inspect-only. Camera providers now write into a unique `captures/.staging/shot-NN-<random>/capture.jpg` directory. The workflow fully decodes and syncs that JPEG, then publishes to `capture-NN.jpg` using an atomic no-replace operation (Unix hard link + staged-name removal; Windows `MoveFileExW` without `REPLACE_EXISTING`, with `WRITE_THROUGH`). An interrupted partial file therefore never enters the committed capture namespace; only explicit Continue removes validated stale staging and retakes the missing shot. If a complete capture was published just before the manifest progress update, exactly one committed JPEG may be ahead of the capturing manifest; Continue fully decodes it, reconciles the count, and captures only remaining shots. Larger gaps remain inspect-only. A full-capture recovery skips camera creation and renders from preserved files. A separate output-only retry republishes rendered.jpg without camera/rendering and is claimed atomically against concurrent session starts. A new-session restart uses a new ID and leaves the interrupted directory untouched. The synthetic-only smoke uses `PHOTOBOOTH_SYNTHETIC_ONLY=1`, which disables idle preview and rejects real-camera Start/Continue/Restart; `PHOTOBOOTH_DISABLE_CAMERA_PREVIEW=1` remains a narrower preview-only control. Startup discovery performs bounded JPEG-header checks and verifies the declared frame snapshot digest, while Continue and output-only retry fully decode their preserved JPEG payloads before camera open/publication. Schema-v2 Continue renders from the session-local frame snapshot even if the active Settings frame was changed or removed; legacy schema-v1 recovery retains the original frame-path/digest requirement. Root/Wails tests and vet, root Windows build, Linux compile-only build, Windows Preview production build and a dedicated UI Automation smoke passed. The synthetic UI smoke covered five generated sessions and all recovery actions; it did not open the physical camera and cleaned its isolated TEMP profile. Stage 1 remains open pending physical/target-hardware and broader acceptance. See [SESSION_CRASH_RECOVERY.md](SESSION_CRASH_RECOVERY.md), [ADR 0028](../adr/0028-local-session-crash-recovery.md) and [UI_SPIKE_RESULTS.md](../../tools/ui-spike/wails-v2/UI_SPIKE_RESULTS.md).

## Stage 3 - LAN photo access and optional payment
- Session-scoped LAN download/QR with short-lived authorization.
- Network/interface binding and guest-to-guest access protections.

## Stage 4 - Cross-platform validation and cloud delivery
- Linux build and installation on the selected distribution.
- Camera/printer integration checks on Linux; document differences from Windows.
- Optional authenticated cloud upload/download, retention, deletion, quotas, and cost model.

## Stage 5 - Marketplace and creators
- Creator publishing, validation, previews, versioning, and moderation.

## Stage 6 - Growth features
- Multi-booth/store management.
- Advanced theme editor.
- Animated digital exports, promotions, scheduling, and analytics.
- Additional camera/printer providers based on observed demand.

## Cross-stage rules
- Do not start later stages just because they are technically interesting; satisfy current validation gates first.
- Keep options documented, but implement only validated needs.
- Market sizing, pricing, creator economics, cloud cost, and reliability targets should be based on actual evidence.
- Formal interviews are optional. Real hardware tests and observed product behavior are still required.

### Addendum - 2026-11-03: preserve provider instance across the first recovery Open

- Reviewing the new recovery-close implementation exposed an ownership gap: after CloseForRecovery, the decorator cleared p.active and called openFresh with no candidate, so its first recovery attempt could create a fresh provider instance. ## 2026-11-21 - Customer/Operator mode and authorization contract defined

The mode boundary is recorded in [ADR 0035](../adr/0035-customer-operator-mode-and-auth-boundary.md).

- Process startup always resolves to Customer Mode; operator authorization is process-local and never restored from disk.
- Customer Mode is limited to the current guest session and an allowlisted result projection. Settings, frame packages, retention, interrupted-session details, printer queue/job metadata, local file paths, SMB administration and application exit are operator-only.
- Backend Go authorization is mandatory for every operator-only Wails binding. The prototype binds the full App object into its WebView, so hiding navigation/buttons is not a security boundary.
- Operator Mode is available only after successful local authentication. Return/lock, timeout, OS lock/suspend, process restart and exit revoke the in-memory authorization context.
- Do not change modes during capture/finalization/printer submission/output retry. Wait for safe worker quiescence; do not silently cancel a guest session to open Settings.
- Startup recovery that needs operator action blocks new guest sessions with a generic customer-facing message. Recovery detail remains operator-only.
- Candidate credential UX is one station-level touch passcode, but credential form, inactivity timeout and failed-attempt/backoff policy remain open values before implementation. The current five-minute timeout is a proposal only.
- The app-mode boundary does not lock down the OS desktop or system shortcuts. OS kiosk lockdown remains separate.
- Remote administration remains unchanged and paused under ADR 0031.

**Next step:** choose credential form and timeout/backoff defaults, then implement the Go-owned mode/authorization controller and backend guards before adding the Operator Mode UI. Test direct binding calls, not only hidden buttons.
